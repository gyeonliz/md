# 전체 작업 정리 및 관리 가이드

## 1. 목적

여섯 개 핵심 업무를 하나의 방식으로 관리하되, Unreal/Git 환경과 PC 간 Codex/GPT 작업 문맥 공유, 드론 프로젝트 실제 개발을 먼저 진행한다. 이 문서는 운영 규칙과 백로그의 기준이다. 실제 진행 상태는 저장소 루트의 [`WORKBOARD.md`](../WORKBOARD.md)에 갱신한다.

초기 사용자 컨텍스트에는 완료로 보고된 항목이 없었다. 아래 백로그는 시작을 위한 작업 정의이며, 완료 여부는 실제 검증 결과를 반영한 보드와 `STATUS.md`를 따른다.

## 2. 작업 영역과 우선순위

| 업무 우선순위 | 핵심 업무 | 현재 성격 | 목표 |
|---:|---|---|---|
| 1 | Git | 최우선 | Unreal 프로젝트를 Git/GitHub로 안전하게 공유 |
| 2 | Codex Sync | 최우선 | 메인컴과 작업컴 사이에서 개발 대화·세션·문맥을 이어가기 |
| 3 | Drone | 최우선 | Flight MVP부터 실제 플레이 사이클 완성 |
| 4 | 정보처리산업기사 | 병행 | 개념 → 문제 → 오답 방식으로 준비 |
| 5 | Coding Test | 병행 | C++로 하루 1~2문제 학습 |
| 6 | 전체 작업 정리 및 관리 | 기반 | 모든 작업을 작고 확인 가능한 단위로 관리 |

위 표는 사용자가 관리할 여섯 개 핵심 업무다. 보드에서 사용할 분류 태그는 `Drone`, `Unreal`, `Git`, `Codex Sync`, `정보처리산업기사`, `Coding Test`, `Portfolio`의 일곱 개다. 태그 수가 하나 더 많은 이유는 `Portfolio`가 독립된 일곱 번째 핵심 업무가 아니라, 완료된 여러 업무의 결과물을 취업 자료로 정리할 때 붙이는 교차 분류 태그이기 때문이다. `Unreal`은 엔진 공통 학습/환경, `Drone`은 현재 게임 구현 작업에 사용한다.

### 기반 구축 순서와 현재 실행 순서

- 기반 구축: 먼저 하나의 보드에 상태 열과 태그를 만드는 최소 작업(WM-01)을 수행한다. 이는 다른 업무를 기록하기 위한 짧은 선행 작업이다.
- 현재 실행: 보드가 준비되면 `Git + Unreal → Codex Sync → Drone` 순서로 최우선 업무를 진행하고, 정보처리산업기사와 Coding Test를 병행한다.
- 지속 관리: 전체 작업 정리 및 관리는 한 번에 끝나는 마지막 업무가 아니라, 진행 중 상태와 다음 작업을 계속 갱신하는 기반 활동이다.

따라서 표의 업무 우선순위에서 관리 업무가 기반으로 분류되어 있어도, WM-01의 최소 보드 구축은 실제 실행에서 먼저 수행한다.

## 3. 상태 흐름

```text
Inbox → Todo → Doing → Done
```

### Inbox

- 아직 범위와 우선순위를 정하지 않은 요청·아이디어
- 미정 기능 후보도 이곳에 둔다.
- Inbox 항목을 바로 구현하지 않고 먼저 1~3시간 작업으로 쪼갠다.

### Todo

- 목적, 완료 조건, 선행 작업이 정리된 작업
- 지금 바로 시작할 수 있거나 선행 작업을 명시한 상태
- 우선순위 순서대로 위에서 아래로 배치한다.

### Doing

- 실제로 수정·테스트 중인 작업
- 한 번에 너무 많은 작업을 Doing으로 옮기지 않는다.
- 막히면 막힌 이유와 마지막 확인 결과를 작업 기록에 남긴다.

### Done

- 완료 조건을 충족하고 결과를 확인한 작업
- 파일을 만들었다는 사실만으로 Done 처리하지 않는다.
- 각 카드는 아래 표 또는 카드 본문에 적힌 개별 완료 조건을 만족하면 Done으로 옮긴다.
- Git 설치 확인 같은 개별 카드는 해당 카드의 로컬 완료 조건만으로 Done이 될 수 있다.
- `Git + Unreal 환경 구축` 전체가 완료되었다고 판단하는 기준은 첫 Push, 다른 PC Clone, LFS Asset 확인, Clone한 Unreal 프로젝트 실행 테스트까지 성공한 경우다.

## 4. 작업 카드 형식

```text
제목: [프로젝트] 동사로 시작하는 한 가지 결과
상태: Inbox | Todo | Doing | Done
예상 크기: 1~3시간
목적:
선행 작업:
수정 대상:
테스트 절차:
완료 조건:
결과/문제:
다음 작업:
```

좋지 않은 예: `적 AI 만들기`

좋은 예:

- `[Drone] AI Perception Component 추가`
- `[Drone] Sight 설정 후 Drone Actor 감지 테스트`
- `[Drone] StateTree Alert 상태 생성`
- `[Drone] MG Smart Object 배치`
- `[Drone] AI의 MG 이동 테스트`
- `[Drone] MG 점유 테스트`
- `[Drone] 터렛 공격 상태 테스트`

## 5. 작업 선택 규칙

1. Todo에서 우선순위가 가장 높고 선행 작업이 끝난 카드 하나를 선택한다.
2. 3시간보다 커 보이면 Doing으로 옮기기 전에 더 나눈다.
3. 작업 시작 시 상태를 Doing으로 바꾸고 수정 대상 파일/Asset을 적는다.
4. 완료 조건을 직접 확인한 뒤 Done으로 옮긴다.
5. 테스트에서 새 문제가 나오면 원래 카드의 범위를 키우지 말고 별도 Inbox 카드로 만든다.
6. 미정 후보는 결정 카드와 구현 카드를 분리한다.

## 6. PC를 바꿀 때의 작업 종료/시작 체크리스트

프로젝트 데이터와 Codex/GPT 작업 문맥은 서로 다른 경로로 관리한다.

### 현재 PC에서 작업 종료

- [ ] Doing 카드에 구현 결과와 남은 문제 기록
- [ ] Unreal 프로젝트 변경 파일 확인
- [ ] 필요한 테스트 실행
- [ ] Git Commit/Push
- [ ] Codex/GPT 작업 컨텍스트 저장
- [ ] 인증 정보·비밀번호가 전달 대상에 포함되지 않았는지 확인

### 다른 PC에서 작업 시작

- [ ] Git Pull
- [ ] Unreal 프로젝트가 해당 PC에서 열리고 컴파일되는지 확인
- [ ] Codex/GPT 컨텍스트 로드
- [ ] Doing 카드와 마지막 테스트 결과 확인
- [ ] 같은 Asset을 다른 PC/팀원이 수정 중인지 확인

## 8. 주간 점검

주간 점검에서는 사실만 갱신한다.

```text
이번 주 Done:
현재 Doing:
막힌 이유:
결정된 사항:
여전히 미정인 사항:
다음 Todo 3개:
Git Push 확인:
컨텍스트 전달 확인:
```

미정인 입력, 물리, 멀티플레이, 군/국가, 게임 규칙을 회의나 테스트 없이 결정된 항목으로 옮기지 않는다.
